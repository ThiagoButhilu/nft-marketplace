# API contracts, events and mock scenarios

Contracts are Zod schemas in [`src/api/contracts`](../src/api/contracts). Request and response
types are inferred from them, and the same schemas validate requests in the mocks and
responses in the client, so transport, state and UI share one typed source.

## Conventions

- Base URL: `/api` (`VITE_API_URL`). JSON in, JSON out.
- **ETH amounts are decimal strings** (`"26.846"`), never numbers, with up to 18 decimals.
  The server does every calculation with `big.js`, and the client only formats the values.
- Quantities are positive integers.
- Authentication: `Authorization: Bearer <token>`.
- Visitor cart: `X-Cart-Id: <uuid>` (generated by the client). After login, the user's cart
  takes precedence.
- Order creation requires `Idempotency-Key` (≥ 8 characters, scoped to the user).

### Error envelope

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "…", "fieldErrors": { "email": ["…"] }, "details": {} } }
```

| Status | Codes | When |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Malformed body or missing headers |
| 401 | `UNAUTHENTICATED`, `SESSION_EXPIRED`, `INVALID_CREDENTIALS` | No/invalid token, expired session, wrong login |
| 403 | `FORBIDDEN` | Resource owned by another user |
| 404 | `NOT_FOUND` | Unknown NFT, order, wallet or API route |
| 409 | `EMAIL_TAKEN`, `USERNAME_TAKEN`, `CONFLICT` | Signup/profile uniqueness, duplicate wallet role |
| 409 | `AVAILABILITY_CONFLICT` | Quantity above stock or per-order limit, sold-out edition |
| 409 | `QUOTE_OUTDATED` | Prices/fees/coupon changed since the quote; `details.quote` carries a fresh one |
| 409 | `IDEMPOTENCY_CONFLICT` | Same `Idempotency-Key` with a different payload |
| 422 | `VALIDATION_ERROR` (+ `fieldErrors`), `COUPON_INVALID`, `COUPON_EXPIRED`, `WALLET_REJECTED` | Field validation and business rules |
| 500 / 503 | `INTERNAL_ERROR`, `SERVICE_UNAVAILABLE` | Transient failures (retryable) |

### Cart, quote and order rules

- A cart line respects edition availability and `maxPerOrder` (10). Exceeding either returns
  `AVAILABILITY_CONFLICT` with the limit in `fieldErrors.quantity`.
- At login or signup, the visitor cart (`guestCartId`) is merged into the user's cart, capped
  by availability.
- When a price changes, every cart holding the item keeps the price the visitor last saw. The line
  shows `priceChanged` and `previousUnitPrice`, and the quote carries a blocking `price-changed`
  issue until `POST /cart/acknowledge`.
- `POST /orders` revalidates the quote against the current cart and catalog: prices, stock,
  coupon validity and fee. Any difference returns `QUOTE_OUTDATED` or `AVAILABILITY_CONFLICT`
  with a fresh quote, and the user must confirm again.
- Stock is reserved while the order is `pending`. A `confirmed` order removes exactly the
  purchased quantities from the cart. A `declined` order releases the stock and leaves the cart
  untouched. `confirmed` and `declined` are terminal states.
- The order snapshots lines, prices, coupon, fee and total at creation, so later catalog
  changes never alter the receipt. Transaction hashes and explorer links are simulated.

## Socket.IO events

Path `/realtime/` (`SOCKET_PATH`), WebSocket transport, session token sent as the `token`
query parameter. Each event has a stable `id`, the affected `resource`, the resource
`version` and `occurredAt`.

| Event | Audience | Payload `data` |
| --- | --- | --- |
| `nft.updated` | everyone | `price`, `compareAtPrice`, `soldOut`, `editions[{ id, available }]` |
| `order.updated` | the order owner only (`userId`), while the session is valid | `status`, `transactionHash`, `failureReason` |

Clients must drop events whose `id` was already seen or whose `version` is not newer than the
cached resource. After a reconnect they must reconcile the active resources over REST.

## Mock layer

Everything lives under [`src/mocks`](../src/mocks) and is enabled by `VITE_ENABLE_MOCKS=true`
(on in development and in the demo build). Components, hooks and the Axios client contain no
fake data.

- `fixtures/`: 36 NFTs (4 pages of 9, as in the Figma), 2 users, wallets, coupons and network fees.
- `server/`: domain services (catalog, accounts, cart/quote, orders) over a store persisted
  to `localStorage` (`kurio.mock-db.v1`). Other tabs pick up changes through the `storage` event.
- `handlers/rest.ts`: MSW HTTP handlers. Every route goes through `endpoint()`, which applies
  the scenario (latency, failures, offline), resolves the session and maps errors to the envelope.
- `handlers/socket.ts`: Socket.IO server mock using `@mswjs/socket.io-binding`.

### Scenarios

Select one with `?scenario=<name>`. The name and any overrides passed to `setScenario(name, overrides)` are remembered in `localStorage`, so a configured scenario survives reloads. Reset the data with
`?mock-reset`. Latency jitter comes from a seeded generator, so runs are reproducible.

| Scenario | Behaviour |
| --- | --- |
| `default` | Happy path, 120–450 ms latency |
| `fast` | No latency |
| `slow` / `variable-latency` | 1.5–3 s / 50 ms–2.5 s |
| `out-of-order` | Shorter searches answer later (responses arrive out of order) |
| `empty` | Empty catalog |
| `offline` | Every request fails at network level; sockets are refused |
| `catalog-error` | `GET /nfts` returns 500 twice, then recovers |
| `catalog-unavailable` | Catalog and detail return 503 |
| `network-failure` | First catalog request fails at network level |
| `favorite-error` | Favorite mutations return 500 (optimistic rollback) |
| `session-expired` | Sessions expire 20 s after login |
| `forbidden` | Profile and wallets return 403 |
| `price-change` / `sold-out` | First order attempt changes the price / sells out the first cart item |
| `order-timeout` | The order is created but the first response never arrives |
| `payment-declined` | Payment is declined |
| `wallet-rejected` | Wallet connection is refused |
| `live-market` | Prices of items in carts change every 20 s via `nft.updated` |

### Control API (`window.__kurioMock`)

Exposed once the worker is intercepting. Playwright (or the browser console) uses it to drive
the **server side**; the app still only sees REST responses and Socket.IO events.

`reset()`, `setScenario(name, overrides?)`, `getScenario()`, `expireSessions(userId?)`,
`updateNft(id, { price?, compareAtPrice?, editions? })` (publishes `nft.updated`),
`settlePendingOrders()`, `liveMarketTick()`, `dropConnections()`, `replayEvent(index?)`
(duplicate delivery), `deliverRawEvent(event)` (e.g. a stale version), `recentEvents()`,
`connectedClients()`.

### Limitations of the Socket.IO mock

- `@mswjs/socket.io-binding` fakes the handshake and ignores the CONNECT `auth` payload, so
  the token goes in the query string.
- The binding never pings. The mock sends engine.io heartbeats every 20 s, otherwise the client
  disconnects after `pingInterval + pingTimeout`.
- Only the WebSocket transport is intercepted (no long-polling), and there are no namespaces or rooms.
  Audience filtering happens in the mock.
- MSW strips a leading `/socket.io/` before matching, so the app uses `/realtime/` to avoid
  colliding with Vite's HMR socket.
- The mock runs in the page: closing the tab stops it. Pending orders keep their settlement
  time in storage and are re-armed on the next load.
